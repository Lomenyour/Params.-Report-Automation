# План доработок импорта и паспортов газа

Согласовано с пользователем 30.10.2026.
02.11.2026 после обсуждения пользователь поручил реализовать согласованные
доработки вместе с паспортами газа. Импорт, подтверждаемый маппинг, единицы
давления и история паспортов реализованы. Текущая реализация описана в
разделе 19 `DATA_FLOW.md`; ниже сохранены требования и результаты аудита.
Индивидуальная методика Ижевской ГТУ остаётся отдельной задачей.

## 1. Понятные сценарии работы

- **Расчёт по выбранной книге:** пользователь выбирает основную книгу,
  программа считает по уже заполненному первому листу «Данные».
  Отдельная выгрузка датчиков в этом сценарии не нужна.
- **Расчёт с подстановкой:** пользователь выбирает основную книгу, файл
  датчиков и лист нужной ГТ. Программа переносит показания по датам,
  рассчитывает необходимые производные величины по методике этой ГТ,
  затем выполняет общий расчёт.

Оба сценария сохраняются. Формулировка «чтение готовой книги для ВНА/РХ»
означает первый сценарий; ВНА и РХ — части расчёта, а не дополнительные файлы.
Готовые результаты по-прежнему сначала показываются в приложении.
Excel и Word формируются отдельными кнопками после проверки пользователем.

## 2. Ручное соответствие «датчик → параметр» один раз

Решение пользователя: не разрабатывать универсальное угадывание назначения
всех колонок. Программа читает структуру файлов, пользователь один раз
задаёт соответствия, далее они используются повторно.
Уточнение пользователя: готовые соответствия избавляют от повторного ввода,
но окно проверки и подтверждение маппинга обязательны при каждом новом импорте.

Состояние до реализации (02.11.2026): прежний `data_assembly.py`
ищет строку с `date` и `time`, читает коды из её заголовков и предлагает
назначения из сохранённого JSON либо станционного справочника. Отдельный
служебный блок описаний/единиц датчиков из выгрузки он пока не извлекает.
Чтение этих описаний в пунктах ниже — план доработки, а не готовая функция.

### Первичная настройка

1. Прочитать фактические коды и доступные описания датчиков из выбранного
   листа выгрузки. Учесть, что код, описание и таблица показаний могут
   находиться в разных строках. Отсутствующее описание не придумывать.
2. Прочитать заголовки первого листа «Данные» основной книги. Показать
   доступные параметры и колонки назначения с их исходными названиями.
3. Открыть таблицу настройки: **код датчика, описание, параметр назначения,
   колонка книги, единицы источника и назначения, преобразование единиц**.
4. Пользователь выбирает, какому параметру соответствует каждый датчик.
   Например, датчик температуры перед компрессором назначается на параметр
   «Температура перед компрессором» и соответствующую колонку этой книги.
5. После нажатия кнопки подтверждения сохранить назначения в пользовательский
   JSON для выбранных ТЭЦ и ГТУ. До подтверждения JSON не изменять.
   Разные ГТ и станции не должны получать чужие назначения.

### Уточнённый порядок автоматического назначения — 02.11.2026

Пользователь уточнил: нужен простой импорт с готовыми соответствиями,
а не отдельный сложный конвертер. Добавить второй источник назначений —
справочник вариантов из `for_info/docs/data_example.docx`.

Порядок будущей работы:

1. Пользователь выбирает ТЭЦ, ГТ, основную книгу, выгрузку и её лист.
   Компания берётся из существующего справочника оборудования. Для
   Ижевской ТЭЦ / ГТУ-1 это `izhevsk_tec` / `1` / `t_plus`.
2. Небольшой обработчик поддерживаемого формата читает даты, теги и показания.
   Описания и единицы извлекаются, если они есть в файле. Назначения по виду
   кода или по диапазону показаний не угадываются.
3. Сначала проверить существующие соответствия именно выбранной ТЭЦ/ГТ
   в JSON-справочнике, включая уже внесённые станционные назначения. Если
   профиль есть, заполнить по нему окно маппинга. Ручные исправления и явно
   оставленные неопределёнными каналы имеют приоритет над общими вариантами.
   При изменении набора тегов сохранить известные назначения, а новые,
   отсутствующие или изменившиеся показать для ручной проверки. Наличие нового
   тега не является поводом заменить существующий профиль общим вариантом.
4. Только если соответствий для ТЭЦ/ГТ ещё нет, искать вариант своей компании
   в справочнике примеров. Заполнить назначения по варианту только при полном
   совпадении набора тегов и единственном однозначном результате. Порядок
   колонок значения не имеет; служебные поля даты/времени датчиками не считаются.
5. В любом случае показать окно проверки маппинга: и после загрузки своего
   JSON, и после подбора общего варианта, и при отсутствии готового результата.
   Пользователь проверяет и при необходимости исправляет теги, параметры,
   колонки и единицы. Автоматическое заполнение окна не означает подтверждение.
6. Только после кнопки «Подтвердить маппинг» проверить назначения и сохранить
   подтверждённый набор в пользовательском JSON этой ТЭЦ/ГТ. При отмене или
   ошибке валидации ничего не записывать и не применять неподтверждённые правки.
7. После подтверждения выполнить согласованные преобразования единиц и обычное
   совмещение показаний по датам в рамках запуска расчёта. Правила получасового
   отбора и приоритета пересекающихся данных этим уточнением не меняются.

### Обновление подтверждённых назначений

- Дать возможность открыть и изменить маппинг известной ТЭЦ/ГТ, даже если
  программа заполнила все поля автоматически.
- Если прислан новый тег вместо прежнего, показать известные назначения и
  неназначенный новый тег. Пользователь связывает его с нужным параметром;
  не угадывать замену по похожему названию и не назначать оба тега на одну
  колонку автоматически.
- При подтверждении исправления того же набора обновлять его запись.
  При подтверждении нового набора сохранить актуальную версию для этой
  ТЭЦ/ГТ. Прежний подтверждённый набор оставить в истории для восстановления
  и повторной обработки старых выгрузок; не смешивать его теги с новым набором.
- Для поиска подтверждённого набора сравнивать теги без зависимости от порядка
  колонок, но с сохранением значимых частей кода. Перестановка колонок сама
  по себе не должна создавать новый профиль.
- Обновление одного профиля не меняет назначения других ТЭЦ/ГТ. Сохранение
  делать атомарно с возможностью восстановления предыдущей версии. Ошибка
  чтения существующего JSON не должна молча приводить к перезаписи пустым
  справочником. При ошибке сохранения явно сообщить, что профиль не записан.

Условия сопоставления:

- Допустимо убирать только подтверждённое оформление заголовков: внешние
  пробелы, порядковую метку `[1]` и служебные элементы конкретного формата.
  Значимые части кода, например `XQ01`, `ZQ01`, `ZQ02`, `CP001` и `CP901`,
  не отбрасывать ради получения совпадения.
- Дублирующиеся после очистки теги, один тег для разных параметров и несколько
  подходящих вариантов считать неоднозначностью, а не удачным совпадением.
- Сходство части кодов может служить подсказкой в ручном окне, но не основанием
  для автоматического переноса всего варианта.
- Код `10MKA01FE006` по прежнему решению остаётся до уточнения. Общее описание
  cosφ в новом справочнике не отменяет найденного противоречия его показаний.

### Что хранить в справочнике вариантов

Word остаётся исходным справочным документом. При реализации перенести
проверенные варианты в отдельный JSON: компания, идентификатор варианта,
список тегов и параметров, подтверждённые единицы/алиасы, ссылка на источник.
Пользовательские назначения конкретной ТЭЦ/ГТ хранятся отдельно и имеют
приоритет. Word при каждом расчёте читать не требуется.

В одном варианте документа встречаются несколько кодов одного параметра
для разных ГТ. Не объединять их вслепую в обязательный набор для одной ГТ;
при подготовке JSON явно разделить такие наборы или описать подтверждённые
альтернативы. Пустые, неполные и противоречивые варианты нельзя активировать
для автоматического назначения без проверки. Единицы из названия параметра
не придумывать, если документ их не задаёт.

Проверка источника на примере Ижевской ТЭЦ:

- В документе 18 вариантов, 1–11 помечены «Т-Плюс», 12–18 — «МЭ».
- Близок вариант №2 «Т-Плюс»: 17 непустых тегов, из которых 9 точно совпали
  с 19 фактическими тегами ранее проверенной выгрузки Ижевской ТЭЦ.
- Расход газа в документе — `EKG13FQ319`, в выгрузке — `10EKG21CF002`;
  мощность — `10MKA10CE003XQ01` против `10MBY10CE901ZQ01`.
  Полного совпадения нет, автоматическое применение варианта №2 не разрешено
  самим правилом полного совпадения. После ручной проверки нужно сохранить
  отдельный точный профиль Ижевской ТЭЦ/ГТУ-1.
- Вариант №15 содержит одинаковые теги у разных физических параметров;
  часть остальных вариантов не заполнена. Документ является исходником
  будущего справочника, а не уже проверенным машинным каталогом.

По результатам реализации подготовлен `config/source_variants.json`: 25
отдельных наборов после разделения вариантов нескольких ГТ, 14 разрешены
для точного сопоставления; неоднозначные и пустые записи отключены.
Исходный Word не изменён. Ижевская выгрузка не совпадает полностью ни с одним
разрешённым вариантом и требует ручного подтверждения своего профиля.

### Что использовать из конвертера Серовской ГРЭС

Полезны небольшие части чтения поддерживаемых форматов, извлечения метаданных,
нормализации служебного оформления тегов и контроля повторов/пропусков.
Встроить их в этап чтения входной выгрузки перед назначениями, без отдельного
обязательного промежуточного Excel. Массовое объединение папки, временная
SQLite и правило «последняя строка получаса под временем его начала» для
согласованного сценария не требуются и автоматически не переносятся.

Проверка перед заимствованием (02.11.2026): изолированно проверены вспомогательные
функции, без запуска конвертера целиком. Разбор обычных чисел и известных
служебных обёрток тегов пригоден как основа. Но исходный код не распознаёт
короткий год и миллисекунды через двоеточие из Ижевской выгрузки; неверно
разбирает трёхбуквенные колонки Excel (AAA, XFD); принимает разные единицы
одного тега без сообщения. Его изменение временных отметок не соответствует
нашей политике. Эти части не переносить без исправления/замены стандартными
средствами и проверок на поддерживаемых форматах.

При реализации читать выбранную выгрузку один раз на этап подготовки,
переиспользуя результат для метаданных, тегов и проверки назначений. Поиск
соответствий выполнять через словари и наборы тегов, а не повторное чтение
книги для каждого датчика. Реальную скорость и результат на входных файлах
проверять после интеграции; проверка нескольких функций сама по себе не
доказывает корректность и производительность всего приложения.

Получасовой режим сохраняется: отбирать имеющиеся измерения на отметках
`:00` и `:30`, без переноса произвольных отметок на границу получаса,
усреднения, интерполяции и подмены «последней строкой интервала». Согласованное
отдельное правило исправления технических долей секунды основной книги
не является разрешением группировать по получасам произвольную выгрузку.

### Повторная загрузка

- Подставлять сохранённые назначения для известных кодов автоматически
  в окно проверки; всегда давать ручную правку и требовать подтверждение

- Буква Excel — положение колонки в конкретной книге. Не считать, что один

- Неизвестный канал можно оставить до уточнения с явным статусом. Его сырые
  показания сохраняются отдельно, без выдуманного назначения и масштаба.

  быть видно как отсутствие необходимого входа.
- Согласованное исключение: `10MKA01FE006` пока остаётся неопределённым.
  Не назначать его на cosφ и не подбирать коэффициент пересчёта по величине
  показаний. Вернуться к нему после уточнения у станции.

### Раздельные перепады

ВЛО, ФГО, ФТО и ФГО+ФТО — разные параметры. Сохранять фактическую структуру
каналов станции. Пустой ФГО не превращать в ноль, а ФТО — в сумму ФГО+ФТО.
Для графика использовать доступные показания. Если расчётная поправка требует
суммарного перепада, отдельно определить её входы по методике станции;
отсутствующие измерения не восстанавливать простым переименованием.

## 3. Явная обработка единиц давления

Согласовано добавить распознавание/ручное указание единиц и явный перевод
к единицам, ожидаемым расчётом. Простого распознавания похожего заголовка
недостаточно: название параметра и единицы — отдельные сведения.

- Атмосферное давление в кПа переводить в Па: ×1000.
- Абсолютное входное давление в мбар переводить в Па: ×100.
- Выходное давление в бар переводить в МПа для текущего расчётного
  интерфейса: ×0,1.
- Различать абсолютное давление и потерю давления на входе; это разные
  физические параметры, даже если исходные заголовки похожи.
- Сохранять исходные значения и единицы, показывать выбранное преобразование.
  Не применять перевод повторно к уже нормализованным данным.
- При неизвестных/противоречивых единицах требовать ручной настройки
  соответствующего параметра, не выводить масштаб молча из величины чисел.

Доработка единиц и назначений не разрешает применять формулы и поправки СызТЭЦ
к другой станции. Пересчёт производных колонок требует методики конкретной ГТ.

## 4. Несколько паспортов газа с датами действия

### Окно «Паспорт газа»

Согласован следующий сценарий:

1. По кнопке открывается окно со списком сохранённых паспортов выбранной ТЭЦ/ГТ.
2. Кнопка **«+ Добавить паспорт»** добавляет ещё одну запись.
3. Для каждой записи задаются даты действия и параметры: плотность, Qнр,
   C/H и компонентный состав. Сохраняются явные единицы.
4. Если паспорт один и действует на весь расчётный диапазон, вводится одна
   запись на весь диапазон. Если паспорта меняются по месяцам или иным датам,
   вводится несколько записей с соответствующими сроками.
5. Записи можно редактировать. При следующем выборе этой станции/ГТ
   сохранённый список загружается автоматически, его можно проверить и изменить.

Месяц — частный случай срока действия. Не предполагать, что каждый паспорт
начинает действовать строго первого числа, если документ этого не подтверждает.

### Хранение и применение

- Хранить историю в пользовательском JSON, чтобы она сохранялась между
  запусками программы. Сохранять принадлежность к ТЭЦ и ГТУ; существующая
  изоляция профилей `station_id|unit` не должна потеряться при расширении.
- Реальные паспорта и пользовательские JSON не включать в Git.
- Для каждой строки измерений выбирать паспорт по её дате автоматически.
  Параметры газа становятся построчными входами, а не одной константой
  на всю историю.
- Сначала рассчитать зависимые величины с паспортом соответствующей строки,
  затем выполнять общий расчёт, регрессии и сводные таблицы.
- Не усреднять несколько паспортов в один квартальный и не интерполировать
  их значения без отдельного согласования.
- Не переписывать старую часть истории последним введённым паспортом.
- Смена паспорта сама по себе не разбивает исследовательские периоды.
- В снимок результатов и экспорт включать использованную историю паспортов
  с датами действия. Экспорт использует снимок расчёта, а не перечитывает
  изменившийся позднее JSON.
- Изменение паспортов требует перерасчёта до формирования актуальных отчётов.

### Проверки при реализации

- На одну дату должен приходиться ровно один применимый паспорт.
- Пересекающиеся сроки запрещаются. Непокрытые даты показываются явно;
  соседний или первый паспорт не подставляется молча.
- Границы сроков обрабатываются без двойного применения. Внутренне допустимы
  полуоткрытые интервалы [начало; следующее начало); интерфейс должен понятно
  объяснять пользователю, какой день/момент включён в выбранный срок.
- Сохранить совместимость существующих JSON с одним паспортом: при обновлении
  не терять значения и не придумывать неподтверждённые исторические сроки.
- Даты начала/конца и типы значений проверять; часовой пояс должен соответствовать
  временной шкале измерений, без скрытого сдвига дат.
- При последующем переносе в БД сохранить те же понятия: владелец профиля,
  паспорт, начало/конец действия, параметры и источник записи.

## 5. Границы текущего согласования

Реализованы reader, маппинг и история паспортов. Газозависимые величины
пересчитываются построчно в существующей подключённой методике СызТЭЦ.
Индивидуальная методика Ижевской ГТУ и уточнение неизвестного канала остаются
отдельными вопросами. Расчётные фильтры, периоды, дискретность, часы и экономику
этот план сам по себе не меняет.
